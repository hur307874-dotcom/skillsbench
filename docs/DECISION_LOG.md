## 第一轮：v1 → v1.5（用户否决叙事角度）

**v1 设计**：被评 Skill 选"无偏量化回测"（教 agent 避免未来函数/幸存者偏差），
叙事主线是"把量化里诚实回测的方法论搬到 Skill 评测"（样本内外、Deflated Sharpe 类比）。

**用户反馈**："不用什么量化背景，就题论题。"

**教训（已记录为用户偏好）**：方案设计不要套用户既有背景讲故事，直接从题目要求出发推导。
选题随之改为 systematic-debugging（纯流程型）。

## 第二轮：v1.5 → v2 初稿 → v2（用户供稿 + 内部评审 + 外部评审 9 点）

**用户提供了自己（或另一 AI）写的 DuckDB/SQL 方向完整方案**，质量很高
（任务 schema、自研 runner、统计方法、防过拟合、归因器俱全）。

**内部评审发现的 4 个问题**（全部被采纳）：
1. SQL 是 LLM 训练覆盖最充分的领域，baseline 可能 >85% → 引入 **Pilot Gate**（先测裸模型再定方向）；
2. pass^k 术语误用（"8 次全过"不是 pass^k）→ 改 n/n 一致通过率；
3. t09 性能任务墙钟判分不稳 → 改确定性代理指标；
4. 矩阵 1200 run 成本超支 → 砍到 ~300。

**开源生态调研**（同期完成，全部核实 URL）：
- SkillsBench（arXiv:2602.12670）：+16.2pp 平均、软件工程仅 +4.5pp、简洁 +18.9 vs 详尽 +5.7；
- SWE-Skills-Bench（arXiv:2603.15401）：**39/49 公开 Skill 零增益（平均 +1.2pp）、token 最高 +451%**；
- agent-skills-eval（npm v0.1.1）：轻量对照工具。
- 结论：现有工作都是静态基准，没人做"归因→修改→再验证"闭环 → 差异化定位确立。

**外部评审第一轮 9 点**（全部采纳，2 点做了选择）：
| # | 批评 | 落地 |
|---|------|------|
| 1 | SQL 只吃"知识"通路（模型最强一档），流程型 Skill 归因故事更强 | 选题改**混合型**数据管道 Skill（知识+流程双成分，消融可分离） |
| 2 | 漏了 Skill 最常见失效：根本没被触发；两家 harness 注入语义不同是直接比较的 confound | 新增 **auto/forced 双臂 + skill_invocation_rate**；跨 harness 只比 forced |
| 3 | n=5×10 任务统计功效不够，有效样本是任务数 | 任务 10→**20**（dev12/heldout8）× n=3；**cluster bootstrap 按任务重采样**；预先登记改为"主张方向+逐任务模式，不主张 p<0.05" |
| 4 | t09 并行污染墙钟；缓存键缺 rep 序号；可复现口径含混 | plan_probe 代理指标；缓存键加 rep；区分 **judgment vs execution reproducibility** |
| 5 | 单任务 judge 算 κ 样本不够 | 选了"升级"路线：**process_judge 贯穿所有 run**（过程质量副指标），t10 降定性展示 |
| 6 | 工期不现实；per-task Dockerfile 过度 | **共享镜像+fixture**；Codex 降为移植性小矩阵；里程碑改纵切优先 |
| 7 | 相关工作可能不存在，引用前必须核实 | 全部核实通过（见上），URL 写入 README/PLAN |
| 8 | 两个便宜加分项 | **placebo 臂**（分离内容效应与注意力效应）；**trace 灌 DuckDB** 可 SQL 下钻 |
| 9 | "模型升级"措辞不准 | 区分**跨代同档**（真升级）与同代跨档（能力强弱），报告分开标注 |

## 第三轮：v2 → v3（外部评审第二轮，概念性重构）

这轮评审被认为是三轮中最有价值的，三个错配：

**错配①（概念性，触发方法论重写）**：
"你把 Skill 当成有版本号的黑盒，而它其实是**一组可以逐条检验的断言**。"
- v2 的消融是"砍 examples 段/砍 checklist 段"——粗粒度、事后补的；
- v3 改为：SKILL.md 每条指令 = 一个独立假设，manifest 映射到失效模式与验证任务，
  **逐条消融（A1-x1..xk）升为主实验**；报告核心粒度从"v1 比 v0 高 12pp"变为
  "**7 条指令里 3 条有效、2 条无效、1 条有害**"。

**错配②（选题，第二次被戳同一处）**：数据管道 Skill 知识成分仍然偏重。
→ 改为「**陷阱代码库中的 API 迁移/缺陷修复**」：知识=非显然 API 规则，
流程=穷举调用点→修改→验证计数；判分=隐藏 pytest+完整性断言（应改 N 处改了/漏了几处）。
原数据管道方案记入"否决项记录"作答辩素材。

**错配③（广度挤深度）**：矩阵砍到单主模型跑全臂；模型 B 只做 A0/A1/A2×8×n=2；
grader 四类砍两类；per-task Dockerfile 彻底删除。

**七个步骤全部落地**：
1. **失效模式清单（F-ID）先行**：D0 第一件事；任务、指令、归因三者共用 ID 体系——
   归因从"看看发生了什么"变成"预登记矩阵哪些格子动了"；
2. **v1 必须是真实的"十分钟版"**：写完 git commit 冻结，之后改动必须由数据触发；
   加社区 Skill 小矩阵做外部效度（防"自导自演"质疑）；
3. 双成分域（见错配②）；
4. 臂设计定稿：A0 / A0p / A1 / A1f / A1-x1..xk / A2 + skill_read_rate；
5. 预算压任务数和臂数：20 任务 n=3、单主模型全臂、跨代对比优先；
6. 里程碑 D0–D6 **纵切优先**，trace schema 在 D1 定死；
7. **预先登记以 git commit 时间戳存证**；报告设"被证伪的假设"专节。

另外确立了**最终交付标准**（反向决定一切建设项的去留）：

> 报告开头第一句话应该能写成："v1 在 dev 上 +12pp，但在 t04/t11 上更差——
> trace 显示 checklist 诱导过度验证；消融确认由第 3 节单独引起；v2 删除后 +14pp、
> token 反降 30%；heldout 复现 +11pp，第二个模型衰减到 +5pp。"
> 整个系统的存在意义就是为了能写出这一句话。

## 第四轮：v3 → v4（外部评审第三轮：文献对位 + 招牌结论的统计存活性）

**① 差异化声明被新文献击穿（事实性错误，必须改）。**
评审检索出四篇直接相邻工作，我们逐一核实为真（arXiv 页面 + 数字一致）：

| 工作 | 撞上的旧声明 | 核实结果 |
|------|-------------|---------|
| SkillAxe（arXiv:2606.10546，Microsoft） | "没人做指令级归因/触发量化" | 真：四维诊断含触发精度（embedding 静态）+ 规则级故障归因 |
| SkillTriage（arXiv:2608.11888） | "误导性失败"是我们的卖点 | 真：307 例 skill-induced failure 分类；最大源=过度验证 67 例 |
| SkillRevise（arXiv:2606.01139） | "归因→修改→再验证闭环"独有 | 真：trace 条件化修订，SkillsBench 36%→61.6% |
| WikiSkill（arXiv:2608.27454，Google） | —（佐证） | 真：自述不评估 retrieval/triggering，触发环节仍是公认缺口 |

**定位重写**（不改任何实验设计，只改表述）：
他们是**自动优化框架**（LLM 改 Skill、终点分数自证，归因喂给下一轮编辑，不预登记不控过拟合）；
我们是**测量与证据系统**（预登记 git 存证、placebo、heldout、人工校准、被证伪假设专节）。
一句话：**它们让 Agent 改 Skill，我们让人知道该信什么。**
另有两个站得住的技术区分：SkillAxe 的触发指标是 embedding 静态距离，我们的 skill_read_rate
是真实 harness 行为观测；SkillTriage 的"过度验证"发现反过来成为我们 F11 的先验证据（互证而非撞车）。

**② 招牌结论在统计上立不住（最重要的技术修正）。**
每条指令的消融只有 verify_tasks × n=3 ≈ 9–15 次 run，pass rate 差值 CI 宽约 ±30pp，
"3 有效 2 无效 1 有害"会得到 7 条全跨零的区间。
→ 指令级结论改走**中介链**：① 消融臂测「指令→行为」（二元行为信号、效应量大、高功效）；
② 全部 ~500 run 测「行为→结果」（样本充足）；③ 合成三分法
（有效=①∧②；无效=①不成立；有害=①∧②反向）。
附带回答了一个 SkillAxe 类工作回答不了的问题：指令没起作用，是 agent 没照做，还是照做但没用。
② 为观察性关联，报告主动披露并以消融臂作准实验佐证。

**③ 可行性修正（全部采纳）：**
- 任务编写量是三倍于 D2 预算的炸弹（20 任务 × 1 正 3 错 = 80 份解法）
  → **任务族生成器**：7 族 × 3 实例 = 21 任务，成本≈7 个；dev/heldout 按族内实例切分；
- 消融臂只在各指令的 **verify_tasks** 上跑（PLAN/ARCHITECTURE 不一致已修正，省约 270 run ≈ 一半预算）；
- 人工校准 20%（100+ 条）→ **分层抽样 40 条**；归因抽检 30–40 条且"有害"判定优先；
- 砍掉跨代模型对比（旧模型 API 可得性是外生风险）；保留模型 B 稳健性（更关键）；
- **D0 第一小时验证 headless 自主触发**（A1 臂的性命攸关前提；无原生加载事件则用
  文件路径匹配推断，写进归一化层）；
- **WSL2 升为默认环境**（非 fallback）；本机 codex CLI 损坏已记录待修；
- placebo 改**同域、听起来合理、不针对任何 F-ID** 的内容（明显无关的会被一眼忽略）；
- skill_md5 → skill_content_hash + instruction_ids；
- `make reproduce` 增加**自验证**（重算分数与原始 score.json 逐条比对，输出一致性报告）。

**总评摘录**：方法论水准已超出题目预期（研究级设计）；动手前改四件事——
差异化重写、中介链、任务族生成器 + verify_tasks 裁剪、D0 触发验证 + WSL2。

## 第五轮：v4 → v5（用户方向性决定：独立全栈应用，不引入 Claude Code）

**用户决定**："不要引入 Claude Code，这个我们是要做成一个独立的有前端有后端的应用的。"

**架构后果（收益大于代价）**：

1. **v4 最大单点风险消除**：headless 模式下 Claude Code 是否自主触发 Skill——
   这个未验证假设整条作废。自研 mini-harness 实现 agentskills.io 规范的
   progressive disclosure（Discovery 清单 → Activation 模型发起 read → Execution），
   auto 触发语义透明、skill_read 成为**原生事件**（不再需要路径匹配推断）；
2. **trace 从"解析别家输出"变为"原生记录"**，无信息丢失、无格式归一化层；
3. **代价**：自研 agent loop（最小 6 工具，纵切只需 3 个）+ 前端四页面
   （看板 / trace 下钻 / 报告 / skill 编辑，P1 可砍）；
4. **跨 harness 硬性要求的处理**：Skill 严格按开放规范书写 + 我们的加载器作为
   规范参考实现 + codex 实证小矩阵降为 stretch（本机 codex 已损坏）；
5. **新的诚实声明**（ARCHITECTURE §2.4）：自研 loop 与 Claude Code 行为不完全相同，
   结论以 forced 臂为主（注入语义跨 harness 一致），auto 臂结论限定于
   "模型自主触发行为"这一现象本身；
6. **前端成为交付物亮点**：trace 逐步下钻查看器即"让人知道该信什么"的产品化呈现，
   答辩演示从"讲 PPT"变成"操作系统"。

**里程碑调整**：D0 不再需要 headless 探针，改为 F-ID 清单 → pilot 任务 → Pilot Gate
（API 脚本手跑，不等 harness 完工）；D5–D6 插入前端接通真实数据；总工期 7.5–8.5 天。

### v5.1 补丁：跨平台兼容性实证升回必做（用户追问触发）

用户追问："但是要在 claude code、codex 等主流平台都能使用啊，这样可以吗？"

澄清一个被 v5 模糊掉的区分：**题目要求的宾语是 Skill（可移植），不是评测系统（必须建在他们上）**。
仪器独立与 Skill 可移植本不矛盾——Skill 按 agentskills.io 规范书写即 Claude Code/Codex
原生格式。但 v5 把实证小矩阵降为 stretch 是降过头了："按规范写的所以兼容"是嘴炮，
答辩需要"真的在 Claude Code 里跑过"的证据。因此：

- 兼容性验证模块 `scripts/compatibility/` 升为**必做**：静态规范检查 +
  claude CLI（本机可用）与修复后的 codex 各跑 dev 6 × A0/A1f × n=2（共 24 run，
  不进主分析）+ 报告"移植性验证"专节 + 前端"导出到 Claude Code/Codex"按钮；
- codex CLI 从"stretch"升为**必修复**；
- 原则记档：**架构不依赖 ≠ 不做兼容性实证**。

### v5.2 补丁：执行流程重排（后按用户要求去掉工期数字）

v5 的里程碑是在"无前端"假设下排的，"前端四页面 1 天""主矩阵+并发 1 天"不现实。
v5.2 三条推进原则：① **矩阵无人值守跑，等待时间做前端和分析**；
② **报告生成器先于前端**（先 markdown 直出，前端只读 traces.duckdb，不阻塞主链路）；
③ **交付分三层带砍单线**（T1 核心闭环 S0–S6 / T2 完整版 S7–S9 / 砍单顺序：
codex 实证 → 看板美化 → 社区 Skill → 模型B 缩减；骨架不可砍）。
随后用户指示"不用具体工期，就写具体流程"——阶段表改为 输入→动作→产出（通过标准） 格式，
按通过标准推进，不设天数。

### ② 放弃自研 harness（推翻 v5 的核心架构决定）

自研方案只能靠"按规范写所以兼容"的论证 + 一个打补丁的兼容性模块；

用户的"独立全栈应用"目标不受影响：应用主体仍是 orchestrator + trace 仓库 + 分析 + 前端，
CLI 的位置相当于数据库驱动——可替换的执行后端，不是应用本身。

### ③ 形态三次修正，最终回到题意：产品

- **第一版 v6**：为 `diagnose` 定做的仪器 → 被指出"是科研仪器穿了应用的外衣"，
  换个 Skill 什么都用不上，而唯一的接入入口 `/skills` 页却排在砍单线第一位（优先级反了）；
- **第二版**：加"平台层 + 首个案例研究" → 用户追问"不应该给一个 Skill 就能评测出来吗"，
  于是想做 LLM 任务生成器填缺口；
- **定稿**：重读题目原话「选定一个 Skill，**给定一组任务**」——**任务是输入**。
  题目从未要求系统自己造任务。**LLM 任务生成器被否决**：让 LLM 读 SKILL.md 反向造任务

### ⑤ 三处自我审查发现的不足，各配了处理办法

这轮末尾主动审查了新方案，挑出三处并当场补掉：

| 不足 | 处理 |
|------|------|
| `A1-noref` 结论有歧义——若模型压根没读引用文件，两臂无差异本来就该是零，"分层无用"与"没去读"指向完全不同的改法 | **固定解读顺序并随 H3 一起预登记**：先看读取率 → 低则报"触发环节失败"（`A1-noref` 降为佐证）；不低且无差异则报"读了也没用"；不低且更好则 H3 被证伪。三条分支都有信息量，但**不能事后挑** |
| `process_judge` 是唯一"有名字但没设计"的组件 | **按砍单项对待**：主结论不依赖它；rubric 限四条二元判别项（不做 1–5 分制，κ 更难达标）；κ<0.7 仅定性披露；进度紧张整块砍 |
| 20 天的真实瓶颈可能不是串行依赖而是任务集工作量 | 标明 A3 是最可能超期一环；先做 3 个实例走通 A4–A7 再批量生成；真做不完**降为每档 4 个（共 12）**——题目只要求至少 3 个，12 个仍支撑难度分层，比 24 个质量参差好 |

### ⑥ 两处防御性设计（用户采纳推荐）

- **H2 防循环论证**："应改 N 处"是我们自己定的标准，若单独作为得分项就是"用自己的尺
  量自己的假设"。改为**每一处漏改都必须有隐藏测试覆盖**，任务校验器增加一项：
  逐处还原 gold 的单个修改点，确认各自对应的测试转为失败。完整性不再是独立打分项，
  而是"测试会抓住你"；
- **B1.5 全臂冒烟**：主矩阵前插 3 任务 × 全部臂 × n=1（约 20 run），
  **不看结论只查坑**（判分是否合理、trace 是否完整、臂注入是否真生效、成本是否符合预估）。
  730 run 跑到一半才发现任务设计有缺陷的代价太高。

- **H1 主指标修正**：从"是否卡死"改为**浪费的轮次/token**。因为模型很可能自问自答绕过去，
  那样卡死率为 0、H1 看似被证伪，实则**测错了东西**——浪费真实发生了，只是没表现为失败。
  行为信号 `phantom_user_interaction` 同时记录该段消耗的轮次与 token。

### ⑦ 执行流程重排为 A/B 两段

用户明确有 20 天专注工期后，真正的瓶颈是**串行依赖**而非总工时。
改为：**A 段（A0–A7）完全不依赖 API**——含归一化一致性测试（用录制 JSONL 离线测）、
前端五页面（读假 run 数据打通全流程）、以及 **A7 通用性验收（在花一分钱之前验掉）**；
**B 段** API 到位后立刻开跑，跑的同时做分析与前端接真实数据。
