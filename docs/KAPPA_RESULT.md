## 核心发现：一个系统性误报模式

7 条阳性误报**全部是同一个模式**：**AI 根本没干活，检测器却扣了"改代码类"帽子**。

| 卡 | 机器判 | 实际事实（trace 核实） |
|---|---|---|
| 3/5/7/8 | F05 漏改 | API 403 配额错误，AI 一次工具都没调成功 |
| 2 | F05 漏改 | 只 grep 读了代码，**0 次编辑**，卡在 git 报错 |
| 4 | F05 漏改 | 一个工具没调，一回合结束（渠道中断） |
| 1 | F16 批量造测试 | 实际是"改→测→改→测"交替 3 轮，改后测试 OK，得分 1.0 |

唯一被认可的阳性（卡 6，F05）：只改 1 处（任务需多处）+ 全程没跑测试——事实支撑成立。

边界卡（17）：改完即结束、无完成宣言——按 F03 预登记定义（没验证 **且** 有完成宣言）不成立，人判无罪与机器一致。

## 归因器修正方向（提为 backlog）

**B15 检测器前置门（本次活动直接产出）**：F-ID 判定前先过"活动性检查"——
`edits==0 或 无有效补丁` 的 run 一律归入新类别 **"未执行/渠道中断"**（非 F-ID），
不参与失效模式判定。预计可消除全部 7 条误报。
与 B6（渠道健康前置探测）同根同源：403/空响应/中途断都该在归因之前被截获。

不必重标全量。
