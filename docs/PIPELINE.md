# PIPELINE — skill-bench 产品全通路（v6 口径）

> 这份文档描述产品从"用户丢进两样东西"到"拿到一份可信报告"的完整通路：
> 每个阶段做什么、数据以什么形态流动、人在哪里介入、质量门在哪里。
> 一句话总览：**输入一个 Skill + 一组任务，系统把剩下全部干完。**

---

## 0. 总通路图

```
用户输入                     系统流水线（全部自动化，人工仅 3 个介入点）
─────────────────────────────────────────────────────────────────────────

① Skill 目录（必需）──┐
                       ├─▶ [G1 入口校验] ──✗ 不合格当场报错（指出哪条）
② 任务集（可选， ────┘
   默认用内置测试集）
                     │
                     ▼
               [S1 指令拆解]  规则切分 SKILL.md → 候选指令列表
                     │  系统 LLM 预填登记草稿（F-ID/行为信号/verify_tasks）
                     │  ✋人工介入点 1：只勾选确认，不从零解释
                     ▼
               manifest.yaml ──[G2 预登记 git commit，时间戳存证]
                     │
                     ▼
               [S2 矩阵生成]  臂 × 任务 × 模型 × 重复 → ~700 个 job + 成本预估
                     │
                     ▼
               [S3 执行]  每个 job：复制 fixture 进 Docker 容器
                     → claude / codex 真实 CLI 按臂注入
                     → 原始事件流原样留存
                     │
                     ▼
               [S4 归一化入库]  两家 JSONL → 统一 trace → DuckDB
                     │
                     ▼
               [S5 判定]  隐藏测试判分（纯函数）+ 行为信号检测（纯函数）
                     │
                     ▼
               [S6 分析]  统计（cluster bootstrap）+ 中介链 + 归因器
                     │  ✋人工介入点 2：分层抽检 40 条校准
                     ▼
               [S7 报告]  对照表 / 热力图 / 指令三分法 / trace 下钻 / 被证伪假设
                     │
                     ▼
               [S8 闭环]  一次改一条指令 → v2 → 重跑 → heldout 一次性终验
                     │
                     ▼
               [G3 make reproduce 自验证] ── 重算分数与原始逐条比对
```

**人工介入点总共只有 3 个**：指令确认（S1，系统预填草稿，人只勾选）、分层抽检校准（S6）、v2 修改决策（S8）。
其余全部自动——这是"产品"和"课题作业"的分界线。

---

## 1. 输入侧：用户提供一样东西，系统自带另一样

| 输入 | 格式 | 谁提供 |
|------|------|--------|
| **Skill 目录**（必需） | agentskills.io 规范：`SKILL.md` + frontmatter + 可选 scripts/ references/ | 用户 |
| **任务集**（可选） | 每任务一个目录：`fixture/`（残缺仓库，agent 唯一可见）+ `solution/`（gold）+ `tests/`（隐藏 pytest）+ `meta.yaml`（完整性断言 + 难度/F-ID 标签） | **默认用系统内置的缺陷修复域测试集**（一个自带代码仓库 + 参数化实例）；用户也可换成自己的 |

内置测试集的安全边界：**它与任何具体 Skill 无关、不为被评 Skill 的指令定做**——
因此不构成"被考的人出考卷"（那条红线针对的是从 SKILL.md 反向生成任务）。
用户只需丢进一个 Skill 就能开跑；换自己的任务集时走同一套 G1 校验。
产品是通用的：换一个 Skill（+ 可选换任务集），**不改任何代码**就能出报告（A7 通用性验收）。

## 2. G1 入口校验（第一道质量门）

- **Skill 校验**：frontmatter 字段完整、目录结构合规；
- **任务校验器**（`skill-bench validate-tasks`，四条全过才收）：
  1. meta 字段完整（难度、F-ID、sites_required、forbidden_edits）；
  2. **gold 解跑通隐藏测试**（答案本身是对的）；
  3. **典型错解被判负**（判分器不是只会打勾）；
  4. **逐处漏改都有测试覆盖**——把 gold 的每个修改点单独还原，对应测试必须转为失败
     （这是 H2 防循环论证的硬约束："应改 N 处"不是我们嘴说的，是测试会真的抓你）；
- 不合格当场报错并指出具体哪一条——**判分可信是整条通路的信用地基**。

## 3. S1 指令拆解（Skill → manifest.yaml）

```
SKILL.md（303 行）
  │  规则切分（按标题/列表项/强制语气句 must-never-always，不用 LLM——可复现、零成本）
  ▼
候选指令列表（带行号和原文）
  │  系统预填登记草稿（LLM 辅助）：建议的 F-ID、从信号库选的行为信号、
  │  建议 verify_tasks、草拟预测
  │  ✋ 人工介入点 1：只勾选/合并/改选确认——不让用户从零解释
  ▼
manifest.yaml ──▶ [G2 预登记 git commit]（假设先于数据，时间戳为证）
```

登记草稿用 LLM 预填不破坏可信度，四条理由：

1. **草稿只是草稿**——最终以人确认并 git commit 的 manifest 为准；
2. 登记发生在实验之前，**LLM 接触不到任何实验数据**，不存在"让 AI 帮 Skill 作弊"的通道；
3. 行为信号**只能从信号库里选**（保证每条都有对应的纯函数检测器），不是自由文本发挥；
4. LLM 的使用全过程记入 AI 使用记录（题目本来就要求讲清楚）。

产物示例（`tdd` 的 I1）：

```yaml
- id: I1
  text: "Confirm with user / Get user approval（L51-56, L58）"
  targets: [F15]                      # 等待不存在的用户
  behavior_signal: phantom_user_interaction   # 纯函数检测器
  verify_tasks: [d1-*, d2-enum-*]
  prediction: 有害（无人值守下诱发自问自答空转）
```

## 4. S2 矩阵生成（manifest + 任务 → ~700 个 job）

- **臂**：A0（无 Skill）/ A0p（等长安慰剂）/ A1（自主触发）/ A1f（强制注入）/
  A1-noref（不给引用文件）/ A1-x1..x7（逐条消融，**只跑该指令的 verify_tasks**）/ A2（修订版，后置）；
- **模型**：claude 三档（Haiku/Sonnet/Opus，测 H4 衰减）+ codex 一档（跨厂商稳健性）；
- **任务选择**：按 manifest 声明的 F-ID 与难度档自动从任务集筛选；
- 生成 `matrix.yaml` + **run 数与预估成本**，确认后才允许开跑（前端向导第 4 步）。

## 5. S3 执行（job → 原始 trace）

每个 job 的生命周期：

```
orchestrator 取 job（缓存键命中则跳过 → 幂等、断点续跑）
  → 起 Docker 容器（共享镜像，digest 锁定）
  → 复制 fixture/ 进容器（agent 的工作区）
  → 按臂注入：
      A0   排除 Skill（--disable-slash-commands 等，B1.5 验证过才算数）
      A1   挂载 Skill 目录，模型自主决定读不读
      A1f  --append-system-prompt-file 注入全文
  → claude -p --output-format stream-json / codex exec --json 跑完
  → 原始 JSONL 原样落盘（raw_event_ref，一个字节都不丢）
```

并发 6 路、无人值守；每 run 记录 token/轮次/墙钟（H1 的主指标来源）。

## 6. S4 归一化入库（两家 JSONL → DuckDB）

- 归一化层把 claude / codex 两种事件流映射成统一事件
  （`run_meta / step / tool_call / skill_read / behavior / grade / f_id_hits`）；
- **只映射不丢弃**，原始文件随时可回查；
- 一致性测试：两家各 3 条真实 run，归一化前后事件数、工具序列、token 合计必须一致
  （不靠肉眼，这是 v6 最大技术风险的控制措施）；
- 写入 `traces.duckdb`——前端查看器、SQL 下钻、分析层共用这一个数据源。

## 7. S5 判定（两类纯函数）

| 判定器 | 输入 | 输出 | 特点 |
|--------|------|------|------|
| pytest_completeness | 容器最终状态 + 隐藏测试 | 分数（0–1）+ 改了/漏了几处 | **纯函数、与 harness 无关**——跨 harness 对照几乎免费的根本原因；改测试判负 |
| 行为信号检测器 ×7 | trace 事件流 | 每个行为 0/1（如 phantom_user_interaction、先枚举后动手） | 不调 LLM，有单元测试——中介链①环的功效来源 |

（`process_judge` 为可选副指标，κ<0.7 只作定性，砍单线第一位。）

## 8. S6 分析（分数 → 结论）

三条分析线，共用同一批 trace：

1. **统计线**：cluster bootstrap（按任务重采样 10k）出 CI；FDR 校正；
   口径预登记：主张效应方向 + 逐任务模式，不主张 p<0.05；
2. **中介链**（指令级结论的唯一合法路径）：
   ① 消融臂上「指令→行为」（二元信号，9–15 run 即高功效）；
   ② 全部 run 上「行为→结果」（观察性关联，报告披露 + 消融作准实验佐证）；
   ③ 合成**有效 / 无效 / 有害**三分法；
3. **归因线**：失败先分叉「未触发 / 触发但用错」→ 落 F-ID 格子 →
   LLM 归因器 → ✋ 分层抽检 40 条（"有害"判定优先，κ 与一致率入报告）。

外加一个独有校准：**埋针 Skill**（故意埋 3–4 个已知缺陷的自写 Skill）走一遍，
给出归因器在已知 ground truth 上的准确率——相邻工作都没做这件事。

## 9. S7 报告（先 markdown，后前端）

报告页七件套（每件都可下钻到具体 trace）：

1. 对照表（A0/A0p/A1/A1f/A1-noref 分开报，带 CI 与成本）；
2. 收益-代价散点图（每个 Skill 版本一个点，左上角是"免费午餐区"）；
3. **难度 × 指令热力图**（H1 主视觉：同一条指令在 D1 有害、D3 有效）；
4. 触发表（skill_read 率 × 结果，含五个引用文件的读取率）；
5. 指令三分法表（每条附 trace 证据链接）;
6. **被证伪的假设专节**（git 存证）；
7. 移植性验证专节（真实 claude / codex 上的表现）。

## 10. S8 闭环（结论 → 修改 → 再验证）

```
归因结论 → 一次只改一条指令（commit message 写明依据）
  典型改法（基于 H1–H3 预测）：
    I1 → 难度条件化（"琐碎 bug 无需确认"）——不是删除，是加分支
    I2 → 加完整性前置（"先枚举全部同模式调用点"）
    I6 → 加存在性前置（"无 CONTEXT.md 则跳过"）
→ v2 重跑主矩阵
→ heldout 一次性终验（只碰这一次）
→ 按预登记验收标准判定：heldout 方向不降 + 目标 F-ID 命中率降 ≥50%
  + 过程分不恶化 + D1 档 token 下降（I1 修订的直接预测）
```

## 11. 质量门总览（通路上的五个关口）

| 门 | 位置 | 作用 |
|----|------|------|
| G1 入口校验 | S1 前 | 判分可信的地基 |
| G2 预登记 commit | S2 前 | 假设先于数据，防事后编故事 |
| G2.5 全臂冒烟（B1.5） | 主矩阵前 | 3 任务 × 全臂 × n=1 ≈ 20 run 先查坑（A0 真没加载？A1-noref 真读不到？判分合理？成本符合预估？） |
| G3 heldout 一次性 | S8 | 防过拟合的最后一道闸 |
| G4 make reproduce 自验证 | 交付前 | 重算分数与原始逐条比对——"可复现"是被检验过的声明，答辩现场可跑 |

## 12. 与执行流程（A/B 两段）的对应

- **A 段（无 API 依赖）**：G1 + S1 + 信号库 + 任务集 + S3/S4 的空壳（用录制的 JSONL 离线测归一化）+ orchestrator 用假 run 数据跑通 S5–S7 + 前端假数据全流程 + A7 通用性验收（`diagnose` + 埋针各走一遍 `/new` 向导）；
- **B 段（API 到位）**：B0 纵切定死 trace schema → B1 Pilot Gate → **B1.5 全臂冒烟** →
  B2 主矩阵（跑的同时做分析与前端报告页）→ B3 中介链+归因 → B4 埋针校准 →
  B5 模型梯度 + codex → B6 v2 + heldout → B7 自验证 + 彩排。
